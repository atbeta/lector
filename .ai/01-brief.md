# 产品简报

产品名：**Lector**（拉丁语"读者"）。

## 要解决什么

Typora 收费、闭源，还想把文件管理也做了；MarkText 已复活但定位是**写作**工具，Electron 重，文档树内核会重写用户文件；SoloMD 已转型 Agent 平台（"The editor where agents live"），编辑器沦为载体。NoteFast 是知识库，双击打开一条导入路径，做不到秒开、也不会写回原文件。

AI 时代内容生产被无限放大，瓶颈转移到消费端：**读远大于写**。Markdown 是 AI 内容的事实格式，但市场上没有专注精美的阅读工具。

用户要的是：**双击一篇 md → 立刻看见、读得舒服、顺手能改、⌘S 写回原路径。**

## 定位

独立应用、独立仓库（`~/Projects/lector`）、独立名字。
**阅读优先的纯 Markdown 编辑器。** 不是第二套知识库，不是 Obsidian，不是写作 IDE，不是 NoteFast 的一种模式。

日后配套：菜单里一条「送到 NoteFast 收集箱」（HTTP 导入）。本应用始终不负责那篇笔记的生命周期。

## 真相来源

| | 本应用 | NoteFast |
|---|---|---|
| 权威 | 磁盘上的 `.md` | SQLite block |
| 打开 | 读文件 | 导入副本 |
| 图片 | 相对路径，留在 md 旁边 | `asset:<sha>` 进资源库 |
| 关文件 | 写回或丢弃 | 库里已有一篇 inbox |

## 窗口模型（已锁定）

- **无应用内 Tab。** 一个文档一个窗口。
- **单进程多窗口**（非字面多实例）：双击新文件开新窗口；双击已打开的文件聚焦已有窗口。
- 窗口管理交还给 OS（Mission Control / Alt+Tab）；macOS 用户可用系统原生「合并所有窗口」获得 Tab 体验，应用不自建。
- 理由：Tab 是藏在窗口里的文档管理，是通往「库」的滑梯；且 Tab 状态/恢复/固定是长尾复杂度。

## 成功标准（v1）

1. 应用已在跑时，双击本机一篇普通 md（无图或少量图），**看见正文 < 300ms**（不含 OS 拉起进程）。
2. 冷启动（含 WebView 拉起）目标 **< 1.5s** 看到字；做不到就先出纯文本再切 IR，不许转圈等「引擎」。
3. ⌘S / Ctrl+S 写回**同一个路径**；未改过的段落与打开时字节级一致（见架构「切片保真」）。
4. 中文 IME 在段落内输入不丢字、候选窗跟光标。
5. 粘贴/拖入图片：写入 md 同目录（或 `./images/`），正文出现相对路径引用，**不进任何库**。
6. 没有侧栏文件夹树、没有库、没有标签、没有同步、没有账号、**没有 Tab**。

> 验收现状（2026-09-18）：3/5/6 有自动化或结构性保证；1/2/4 尚缺实测记录，证据与手动清单见 [07-acceptance.md](./07-acceptance.md)。

## 明确不做（防滑坡）

- 文档管理：文件夹树、多库、标签、图谱、全文跨文件搜索、每日笔记
- 知识库能力：block 数据库、收集箱、资源库、MCP、向量、实体
- **AI 功能**：Agent 面板、AI 改写、语义搜索（SoloMD 之路，一概不做；AI 消费交给 NoteFast / 外部 MCP 消费方）
- 嵌 NoteFast engine / 共用 SQLite
- 应用内 Tab、主题市场、社区插件
- 协作、云同步、账号
- v1 不做：PDF 印刷级导出、完整 Pandoc、Vim 模式

可接受的「像文件管理、但不是」：

- 打开 / 另存为 / 最近打开（≤ 20 条，本机 json）
- 当前篇大纲、文内查找替换
- 系统文件关联（`.md` `.markdown` `.txt`）

## 用户与场景

- 主场景：把本应用设为 md 默认打开方式，当「系统级阅读器」用——读 AI 生成内容、读文档、读笔记导出。
- 次场景：从 NoteFast 导出一篇，在本应用里改完，再「送到收集箱」或自己拷回去。
- 非场景：用本应用管理整个笔记库；用本应用写长篇（能写，但不为主场景优化）。

## 平台

v1 必须 **macOS + Windows** 同步可用（呼声来自两端同事），统一 **Tauri 2** 薄壳。Linux 可后做，同一套 Web 编辑器即可。
